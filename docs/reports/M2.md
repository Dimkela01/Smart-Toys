# M2 "Voice loop" — report

A child holds the paw, speaks, and the character answers by voice. Measured over 40 turns
through the real WebSocket with the real models: **p50 first audio 2.5 s (sr) and 2.6 s
(en), p95 2.8 s and 3.0 s**, against NFR-02's p50 ≤ 4 s and p95 ≤ 6 s. 40 of 40 turns
answered.

Scope (`docs/MILESTONES.md`): F-05, F-06, F-07, F-21 (capture only), F-18 (LLM/STT/TTS
languages); UC-11, UC-19, UC-22.

**Status: not finished.** Barge-in, the character states driven by output RMS and the
queue are in; the activity cards still only acknowledge a tap, because the activity engine
is M4. The two items that need a decision from you are in §8.

## 2. What was built

**Three inference services** (`services/inference/`), each resolving its own weights
through `models/registry.yaml` so that no model file name appears in a Dockerfile or a
compose command:

- `llm` — the upstream llama.cpp server image pinned by digest, plus a launcher that reads
  the registry. Two slots of 2,048 tokens, no GPU offload, `--jinja`.
- `stt` — faster-whisper int8 on CPU, `beam_size=1`, VAD on, language forced per child.
- `tts` — Kokoro for English and a Piper voice for Serbian behind one interface.
  `internal_only` voices are refused unless `TTS_ALLOW_INTERNAL_ONLY` is set, so a
  deployment that forgets the flag loses the Serbian voice rather than publishing an
  unlicensed one.

**The turn pipeline** (`services/api/app/orchestrator/`) yields events instead of
returning a result, so the first sentence reaches the voice while the model is still
writing the second. Think-stripping and sentence-splitting are both incremental, because a
tag or a sentence end will arrive split across two tokens.

**`/ws/turns`** speaks the message set in `ARCHITECTURE.md` §7.2. The child client receives
a state name, WAV frames and, on failure, a code — never model text.

**The browser side** (`apps/web/lib/audio/`): an AudioWorklet resamples the context's
48 kHz to 16 kHz mono PCM16 and posts one 20 ms frame at a time; each sentence is scheduled
on the AudioContext clock rather than started from the previous one's end event, which
would leave an audible seam; the paw's ring is the microphone RMS and the character's mouth
is the RMS of the audio actually playing.

**Three tables** — `sessions`, `turns`, `turn_metrics` — with no column anywhere that could
hold audio. The schema test asserts that rather than trusting it.

## 3. Measurements

`make bench` drives the real socket with synthesized questions. 20 turns per language, this
laptop, CPU only, everything in Docker.

| | first audio p50 | p95 | min | max | whole turn p50 |
|---|---|---|---|---|---|
| sr | 2,470 ms | 2,796 ms | 1,191 ms | 2,949 ms | 2,887 ms |
| en | 2,620 ms | 2,950 ms | 1,603 ms | 2,993 ms | 3,109 ms |

Component averages from `turn_metrics`:

| | STT | TTFT | TTS (first sentence) | first audio | decode |
|---|---|---|---|---|---|
| sr | 829 ms | 937 ms | 125 ms | 2,115 ms | 50 tok/s |
| en | 655 ms | 628 ms | 925 ms | 2,391 ms | 57 tok/s |

**The prompt cache is doing most of the work.** Of ~1,000 prompt tokens in a Serbian turn,
~830 come back cached. That is what the block order in `DATA_MODEL.md` §5 is for, and it is
worth protecting: anything that makes the stable prefix vary per turn would cost seconds,
not milliseconds.

### What the first run found

The first 40 turns came out at p50 1,484 ms (sr) and 3,360 ms (en), with English TTS taking
1,829 ms of a 3,242 ms turn and llama.cpp's decode held down to 13 tok/s. The cause was
thread oversubscription: the English voice runs on torch, torch defaults to one thread per
core, and it synthesizes sentence N while the model is still generating sentence N+1 — so
it was starving the model it runs beside. Bounding torch to 4 threads and llama.cpp to 10
took English TTS to 925 ms, decode to 57 tok/s and English p95 from 4,111 ms to 2,950 ms.

Serbian p50 rose from 1,484 ms to 2,470 ms in the same change, which is not a regression in
the pipeline: generation is sampled at temperature 0.7, and the second run's answers were
longer (1.9 sentences and 9.7 s of speech against 1.4 and 5.0 s). Both runs are inside
NFR-02; the second is more even across the two languages, which is what the thread budget
was for.

**These numbers measure latency, not accuracy.** The child's speech is synthesized by our
own TTS, because there are no recordings of children yet — and the Serbian voice
mispronounces the language, so speech-to-text is being fed something no child would say.
See §8.

## 4. Decisions and assumptions

**Audio for the fallback lines is generated, not committed.** `make audio` synthesizes the
three lines from `UI.md` §5 into `apps/web/public/audio/`, which is in `.gitignore`. The
only Serbian voice available is non-commercial, so its audio may no more live in the
repository than its weights may; and the files are regenerated anyway once there is a
recorded voice. A checkout without them is not broken — the character settles back to idle,
which is still no text and no error screen — but it is silent, which is worse than the spec
asks for. Not specified either way in `docs/`.

**The WebSocket authenticates with a subprotocol**, `new WebSocket(url, ["bearer", token])`.
A browser cannot set an `Authorization` header on a WebSocket, and a token in the query
string ends up in access logs and browser history. §7.2 says "child session token required"
without saying how; this keeps the token in the handshake headers, where the header would
have been.

**Binary frames carry a small JSON header.** §7.2 says "header `{turn_id, seq}` + audio";
the concrete encoding is a 4-byte big-endian length, the JSON, then the WAV.

**TTS is sequential within a turn**, not pipelined: sentence N+1 is synthesized after N has
been sent. At RTF 0.02 (sr) and 0.11 (en) synthesis is far cheaper than generation, so a
pipelined version would buy little and cost real complexity. Worth revisiting only if a
measurement asks for it.

**History is scoped to the current session.** Memory across sessions is a
parent-controlled feature with its own table in M5, not something that should leak in
through the history window.

**A failed turn still gets a row**, with its `error_code` and whatever measurements it
reached. A turn that failed halfway is the one worth looking at.

**`piper` is GPL-3.0-or-later.** It runs as a separate service we do not distribute, so for
a hosted product this is a deployment question rather than a code one. A shipped device
profile (D7's reference board) would have to answer it properly. The English path does not
use piper. Flagged here rather than decided.

## 5. Defects found and fixed during M2

Three were found by running the real thing rather than by a test.

1. **Turns produced audio and stored nothing.** Every turn played correctly and the `turns`
   table stayed empty. The row was written after `turn.done` was sent; a client that closes
   the moment it hears `turn.done` makes the receive loop cancel the turn's task, and a
   cancelled task cannot finish a write. The row is now written before the turn is
   announced, and a cancellation during the write leaves the turn unrecorded-so-far, which
   the canceller then records. There is a test with no sleep in it that reproduces the race.

2. **An interrupted turn was never recorded.** The cancelled task tried to store the row in
   its own cleanup, where the first `await` is cancelled too. The canceller writes that row
   now — it is also the only place that knows the turn was interrupted rather than failed.

3. **`getUserMedia` asked for `channelCount: 1` as a hard constraint.** A device that
   cannot capture single-channel fails the whole call rather than handing over stereo we
   could use, and mono is enforced in the worklet anyway. All four audio constraints are
   now preferences.

4. **Releasing the paw claimed the thinking state even when no turn had started**, so a
   device whose microphone would not open left the character thinking forever.

5. **The JSONB list columns had no server default.** Any insert not made through
   SQLAlchemy failed the not-null constraint — found by inserting through `psql`.
   `children.interests` had the same gap since M1 and is fixed in the M2 migration rather
   than by editing an applied one. From M5 the retention and summary jobs write SQL, so
   this would have bitten then.

6. **The published inference ports collided.** 8001 and 8002 are the ports the services use
   *inside* the network, and a machine that had already shifted `API_PORT` to 8001 could
   not start them. They are published on 8090–8092 now.

## 6. A contradiction in the specification

`DATA_MODEL.md` §5 budgets prompt block 1 at ≤ 400 tokens. Measured against the active
model's own tokenizer, the prompt files copied verbatim from `SAFETY.md` §5 come out at:

| | characters | tokens | characters per token |
|---|---|---|---|
| sr | 1,734 | **713** | 2.43 |
| en | 1,701 | **405** | 4.20 |

So the Serbian system prompt is 78% over its documented budget, and English is just over.
Two things follow:

- **§5's total still holds**: 713 + 40 + 60 + 700 + 80 = 1,593 against 1,610, and the whole
  prompt plus a 150-token answer stays inside NFR-04's 2,048. So the code is correct and it
  is the documented line item that is wrong. I have not edited `docs/`.
- **Serbian costs about 1.7× more tokens than English for the same words**, because the
  tokenizer splits its diacritics and endings far more finely. The 700-token history budget
  therefore holds noticeably fewer Serbian turns, so Bruno's memory is effectively shorter
  in Serbian than in English. That is a product fact, not just a number.

The safety rules are never trimmed to fit a budget — half a rule list is more dangerous
than a long one — so history gives way instead, which is what §5 already prescribes.
`estimate_tokens` carries a measured ratio per language, and a test asks the live service
to re-count so the ratios cannot drift unnoticed when the model changes.

## 7. Known issues

1. **No instant sound on release.** NFR-02 asks for a "thinking" sound the moment the paw
   comes up. The character's state changes immediately, but there is no sound until either
   the answer or a fallback line. It needs one short recorded "hmm" per language and
   character, which is the same generated-audio problem as §4.
2. **Answers are long.** 1.9–2.1 sentences and 7.6–9.7 s of speech on average. Inside
   NFR-03's "1–3 sentences", but close to the limit of what a five-year-old will sit
   through. A prompt matter, so M3.
3. **Serbian answer quality is poor.** Asked why the sky is blue, the model produced
   grammatically broken Serbian and, once, an answer that was simply wrong. Qwen3-1.7B is
   much weaker in Serbian than in English. This is what the `docs/EVALUATION.md` benchmark
   and M6's model choice exist to settle; it is recorded here as a first data point.
4. **The activity cards do nothing yet.** A tap is acknowledged and the messages are
   accepted on the socket; the engine is M4.
5. **`llm_rss_mb` and `gpu_mem_mb` are not sampled.** EVALUATION.md §4.1 asks for peak
   process RSS per turn at 100 ms intervals. There is no GPU to measure inside Docker, and
   RSS needs a sampler in the llm container. Left for M6, where the benchmark needs it.
6. **The Docker VM has 7.7 GB, not the host's 48 GB.** The three services use about 4 GB of
   it. Moving speech-to-text to `small` would press on that; worth knowing before trying.
7. **A microphone needs a secure context**, so `make https` is required on a phone. On a
   device where it cannot work, the paw is enabled and the first press fails quietly: the
   character settles back and a parent sees the reason in the console. There is nothing
   parent-facing yet.

## 8. What needs you

1. **A Serbian voice.** You judged the placeholder: it is Serbian, and the pronunciation is
   bad. Its dataset is also CC BY-NC-SA 4.0, so it can never be shown to a buyer. Of the
   alternatives, Meta's MMS has no Serbian voice at all, Chatterbox's 23 languages do not
   include it, the one F5-TTS Serbian finetune is built on CC-BY-NC weights despite its MIT
   tag, and the one clean-licensed option — a Chatterbox Serbian finetune on 100 h of
   parliamentary speech — is a 0.5 B autoregressive model that will not meet the latency
   budget on CPU. The recommendation stands: record a voice actor for a few hours and
   fine-tune a Piper voice. You then own the licence, and the character gets its own voice,
   which for a toy is the product.

2. **Serbian recordings of children.** Everything in §3 measures latency. Nothing measures
   whether the toy can *understand* a four-year-old, and `base` is a small model. The fix if
   it cannot is `small` or `medium`, which costs latency and memory — a decision that needs
   data, and the data cannot come from production use, because audio is never stored.
   A few minutes of consented recordings would settle it.

`google/gemma-3-1b-it-qat-q4_0-gguf` is still gated — accept the terms and export
`HF_TOKEN` if you want the benchmark to include it.
