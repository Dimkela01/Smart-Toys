## 3. What was built

- **Backend** (`services/api`): FastAPI on Python 3.12, async SQLAlchemy 2 over psycopg 3,
  Alembic, Redis for lockouts and rate limits. 25 operations across 22 paths.
- **Database**: the seven tables M1 uses from `DATA_MODEL.md` §2.1–§2.2. Later tables arrive
  with the milestones that use them, so no field is guessed before its milestone defines it.
- **Web** (`apps/web`): Next.js 15 (App Router), TypeScript strict, Tailwind 4. Landing,
  privacy summary, registration, verification, PIN, dashboard, three-step add-child wizard,
  password reset, child picture picker, placeholder toy screen, admin sign-in.
- **Child mode is locked on the server, not only in the UI.** Entering sets `child_mode_at`
  on that device's refresh token, which makes `/auth/refresh` answer `403 child_mode_active`;
  child tokens are accepted only while that flag is set, so exiting or signing out
  invalidates them at once. A UI-only lock would hand a parent session back to anyone who
  reloaded the page.
- **Token audiences** (`parent`, `child_mode`, `child_session`, `admin`) are separated by a
  claim, and crossing them answers `403 wrong_token_type` in both directions.
- Another family's child answers `404`, not `403`, so ids cannot be probed.

## 4. Assumptions

Listed because they are not stated in `docs/`, as required by `CLAUDE.md` §1.5.

1. **Three extra database columns.** `parents.token_version` (a reset invalidates every
   issued token, UC-02 AC), `refresh_tokens.token_hash` (the token itself is never stored)
   and `refresh_tokens.child_mode_at` (the server-enforced child-mode lock).
2. **Migrations are per milestone.** M1 creates only the tables M1 uses.
3. **`child_settings` is created with the child** using the UC-04 defaults and shown
   read-only at the end of the wizard. The screen that edits them is M5.
4. **Changing an existing PIN requires the current PIN.** Otherwise an unattended parent
   session could lock the real parent out of child mode.
5. **Admins get no refresh token.** With 2FA and a 15-minute session they sign in again.
6. **PIN attempts have their own rate-limit bucket** (20/min/IP). With the shared 10/min
   auth bucket from NFR-06, the API answered `429` before the specified `423 pin_locked`
   could appear; the 5-attempt lock is the real control there.
7. **The end-to-end suite runs with a raised auth rate limit**
   (`infra/docker-compose.test.yml`), because it signs several parents in within a minute
   from one address. The limit itself is unchanged for development and deployment.
8. **Child-mode tokens live in `sessionStorage`.** A reload must not strand a child on a
   dead screen, and the parent session cannot be refreshed while the device is locked. The
   token stops working the moment the parent exits or signs out.
9. **`GET /meta/catalog` is open** (no token). It serves versioned content that is identical
   for everyone, and both the parent wizard and the child picker need it. It deliberately
   contains no voice or model ids, which are admin-only; a test asserts that.
10. **`GET /auth/me` and `/admin/me`** are not in `ARCHITECTURE.md` §7.1 but are needed so
    the web app knows which screen to show after a reload.
11. **The verification link signs the parent in** on that device, so the flow continues to
    the PIN screen without a second sign-in.
12. **`ADMIN_SEED_EMAIL` and `SMTP_FROM` use `example.com`.** `admin@localhost` has no TLD
    and the login schema rejects it, so the seeded admin could not sign in at all.

## 7. Known issues and risks

1. **No safety layer is active yet.** There is no router, no fixed responses and no output
   filter, because there is no model to guard. Nothing in this milestone may be shown to a
   child as a working toy.
2. **Demo only.** No real children's data, per D2 and the pre-pilot checklist.
3. **The Serbian TTS voice licence is still unconfirmed.** It is configured as
   internal-only and must not reach a public demo URL.
4. **Production configuration is checked but not enforced.** `check_production_safety()`
   logs a warning when `ENVIRONMENT=pilot` still has a development `JWT_SECRET`, a missing
   `TOTP_ENCRYPTION_KEY`, an insecure cookie or a local mail catcher. Before any pilot this
   should refuse to start rather than warn.
5. **The content security policy allows `unsafe-inline` and `unsafe-eval`** for scripts,
   which the Next.js dev server needs. The production build in M7 should tighten it.
6. **Rate limits and lockouts fail open if Redis is down**, with an error logged. A broken
   counter must not lock every parent out, but it does mean the limits are only as reliable
   as Redis.

## 8. Bugs found while testing, and fixed

Recorded because each was found by exercising the running system rather than by review:

1. The models and the migration disagreed on two `server_default` values; the drift test
   now fails on any such difference.
2. The async Redis client outlived the event loop between tests.
3. `ADMIN_SEED_EMAIL` defaulted to an address the login schema rejects, so the seeded admin
   could never sign in.
4. Setting the PIN left the dashboard still asking for one, because the session state was
   never updated from the response.
5. Signing out raced two redirects, so where it landed was luck.
6. The picker tried to re-enter child mode with a child-mode token, which the API correctly
   refuses; the pictures are now kept from the parent's entering response.
7. The end-to-end suite locked the real seeded admin account by repeatedly failing against
   it; it now uses an address that does not exist.
8. Found on a real iPhone: in landscape the paw was pushed off the fixed, non-scrolling toy
   screen and became unreachable. The character now shrinks into the space that is left and
   the screen respects the safe-area insets.
9. Found on a real iPhone: opening a parent page in a second tab threw "a client-side
   exception has occurred". A new tab shares the cookies but not `sessionStorage`, so it had
   no child-mode token while the device was still locked, and the parent and child screens
   redirected to each other for ever. The child screen now explains the lock instead of
   redirecting.
10. **The same report, one layer deeper: that explanation was a dead end.** Leaving child
    mode went only through `/child-mode/exit`, which needs the child-mode token held in
    `sessionStorage`. Any browser that dropped it — a new tab, a reopened Safari, a restored
    session — could reach neither the toy screen nor the exit, while `/auth/refresh` kept
    answering `child_mode_active`: the parent's account was unreachable on that device for
    good. `POST /auth/unlock` now takes the PIN with the device's refresh cookie instead,
    which is the proof UC-21 asks for; it shares the PIN lockout with `/child-mode/exit`, so
    the second door does not add guesses. The locked child screen offers it behind a button.

## 9. Logic audit after sign-off

A deliberate pass over M1's behaviour, asked for before M2 began. Five defects, three of
them demonstrated against the running stack rather than argued from reading:

1. **The per-IP rate limit was free to bypass** (NFR-06). `client_ip()` read the *first*
   `X-Forwarded-For` entry, which is whatever the caller sent. Measured: 14 of 14 requests
   allowed with a different forged value each time, through the dev proxy as well as
   directly, because Next.js passes the header through unchanged. The header is now read
   only when `TRUST_PROXY_HEADERS` says a proxy we control sets it, and then the *last*
   entry is used. Re-measured after the fix: 60 allowed, then 429.
2. **Two browser tabs could sign the parent out.** Refresh tokens are single use and a
   replay revokes the device, but two tabs loading together both present the cookie the
   browser had, and the loser was treated as a leak. A replay inside
   `REFRESH_REUSE_GRACE_SECONDS` (10 s) is now answered with an access token and no
   rotation; a later replay still drops the device.
3. **Every browser that opened a verification link shared one device identity**
   (`verify-<account>`), so a second device revoked the first's refresh token — and the
   first then tripped the replay check and dropped itself — while entering child mode on
   one phone would have locked the other. `/auth/verify` now takes the client's
   `device_id`, as `/auth/login` already did.
4. **A forgotten PIN could never be reset**, though UC-21 AC asks for exactly that ("reset
   only from the parent login"). Changing a PIN demanded the current one. It now takes
   either the current PIN or the account password; the password is checked against the
   login lockout. The screen for it belongs to M5, so for now this is API-only.
5. `deviceId()` in the web app returned a fresh value on every call when `localStorage` is
   blocked (private browsing), so one device looked like many. It is memoised.
